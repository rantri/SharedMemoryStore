# Phase 0 Research: Open Source Documentation

## Decision: Use GitHub-native repository documentation entry points

**Rationale**: The project is intended to be discovered and evaluated on GitHub,
so first-contact documentation should use familiar root files and `.github`
community health conventions. Root-level `README.md`, `LICENSE`,
`CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md`, `SUPPORT.md`, and
`CHANGELOG.md` make the repository navigable without requiring a documentation
site. `.github/ISSUE_TEMPLATE/` and `.github/pull_request_template.md` provide
structured contribution intake while staying lightweight.

**Alternatives considered**:
- Documentation website: rejected for this feature because the current need is
  GitHub and package readiness, not a separate publishing pipeline.
- Only expanding `README.md`: rejected because security, support, release, and
  contribution policies need stable, linkable locations.
- Wiki pages: rejected because they are less reviewable with code changes and
  harder to validate in CI-like local workflows.

## Decision: Keep behavior documentation sourced from the package and existing contracts

**Rationale**: The docs must not drift from implemented public behavior. The
source of truth for consumer-facing behavior is the current runtime package
surface in `src/SharedMemoryStore`, the XML docs generated by that project, and
the first feature contracts under `specs/001-frame-memory-store/contracts/`.
The open source docs should explain those contracts in consumer-friendly form
and link deeper behavior details rather than restating unverified claims.

**Alternatives considered**:
- Write new behavior promises directly in the README: rejected because it risks
  contradicting public API and layout contracts.
- Treat implementation tests as the only documentation source: rejected because
  consumers and reviewers need narrative ownership, lifecycle, and compatibility
  guidance.

## Decision: Present maturity as prerelease package documentation

**Rationale**: The runtime project currently declares package version `0.1.0`.
Documentation should describe the library as prerelease until the project
explicitly publishes a stable release. This avoids implying a final API,
cross-platform support, binding availability, or production SLA that the current
project has not established.

**Alternatives considered**:
- Claim stable `1.0.0` readiness: rejected because the package metadata and
  release process do not currently show a stable release.
- Avoid status language: rejected because users need to know what is
  implemented, what is validated first, and what remains future work.

## Decision: Use MIT as the license baseline

**Rationale**: `src/SharedMemoryStore/SharedMemoryStore.csproj` already declares
`PackageLicenseExpression` as `MIT`. The repository documentation should add a
matching root `LICENSE` file and keep package metadata, README, and support
policy aligned with that license. The docs should still state that maintainers
own final release approval.

**Alternatives considered**:
- Leave license as undecided: rejected because package metadata already makes a
  concrete license claim that must be reconciled before public release.
- Choose a different license in documentation: rejected because that would
  conflict with the existing package metadata and violate the consistency
  requirement.

## Decision: Use GitHub private vulnerability reporting as the security path

**Rationale**: Public open source repositories need a private vulnerability
reporting route. The security policy should direct vulnerability reports to
GitHub private vulnerability reporting/security advisories for the repository
and instruct users not to disclose exploit details in public issues. If the
repository setting is not enabled during implementation, release preparation
must either enable it or update `SECURITY.md` to another owner-approved private
contact path before publication.

**Alternatives considered**:
- Public issues for vulnerabilities: rejected because the specification requires
  private reporting guidance.
- Personal email address in the plan: rejected because no owner-approved address
  is present in the repository context.

## Decision: Add repository-local documentation validation

**Rationale**: The success criteria require no unresolved placeholders, broken
internal links, or contradictions. A local `scripts/validate-docs.ps1` can check
required file inventory, placeholder patterns, relative Markdown links, sample
README presence, and package metadata alignment without adding a runtime
dependency or requiring a hosted documentation service.

**Alternatives considered**:
- Add Node-based markdown tooling: rejected for this feature because it creates
  an additional toolchain for a small docs set.
- Manual review only: rejected because placeholder and link drift are recurring
  risks in public documentation.

## Decision: Keep documentation clear but not exhaustive in the root README

**Rationale**: The README must let a first-time visitor decide whether to keep
reading in under 10 minutes. It should state the package purpose, status, quick
start, core workflow, constraints, support/security paths, and navigation. Deep
details belong in `docs/` and contract links.

**Alternatives considered**:
- Put all usage and contract detail in README: rejected because the entry point
  would become hard to scan.
- Use only a documentation index: rejected because GitHub visitors expect the
  README to answer basic purpose, maturity, and first-use questions directly.
