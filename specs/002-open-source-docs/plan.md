# Implementation Plan: Open Source Documentation

**Branch**: `002-open-source-docs` | **Date**: 2026-06-27 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/002-open-source-docs/spec.md`

## Summary

Create the public documentation baseline required for SharedMemoryStore to be
evaluated, consumed, contributed to, and released as an open source GitHub
library. The feature is documentation-only for runtime behavior: it expands the
repository entry points, package-facing documentation, usage guides, contract
references, community policy files, release guidance, issue/PR templates, and
validation guidance while keeping claims aligned with the current `0.1.0`
`net10.0` package implementation and the Shared Memory Value Store contracts.

The implementation should preserve and expand the current concise `README.md`,
`docs/lifecycle.md`, `docs/packaging.md`, and `docs/portability.md`, add the
missing common open source documents, and cross-link them from a documentation
index and repository entry points. Documentation must clearly distinguish
implemented package behavior, prerelease status, Windows-first validation,
future C++/Python portability goals, and unsupported scenarios.

## Technical Context

**Language/Version**: Markdown documentation, GitHub community health files,
C# XML documentation generated by the existing `net10.0` package project, and
NuGet package metadata from `src/SharedMemoryStore/SharedMemoryStore.csproj`.

**Primary Dependencies**: No runtime dependency changes. Documentation
validation may use the existing .NET SDK, PowerShell scripts, `dotnet test`,
`dotnet pack`, sample projects, and package-consumption validation. Any optional
Markdown/link validation helper must be repository-local and must not add a
runtime package dependency.

**Storage**: Git-tracked repository files: root documentation, `docs/` guides,
`.github/` issue and pull request templates, sample project READMEs, package
metadata in the runtime `.csproj`, and generated package artifacts during local
validation. No database or external documentation service is introduced.

**Testing**: Documentation validation includes inventory checks, placeholder
checks, internal link checks, package metadata/readme alignment, sample command
verification, clean package-consumption validation, `dotnet test`, and
`dotnet pack` where package-facing documentation is affected.

**Target Platform**: GitHub-hosted open source repository documentation and
NuGet package consumers. Runtime statements target the current C#/.NET 10
package, with Windows x64 named memory-mapped-file validation called out as the
first supported production target. C++ and Python are documented as future
portability audiences, not current bindings.

**Project Type**: Documentation feature for a reusable NuGet package/library.
No runtime behavior, shared-memory layout, public API, or package identity
change is planned except package-facing documentation metadata alignment.

**Performance Goals**: No runtime performance impact. Documentation outcomes
are measured by reader workflows: evaluation under 10 minutes, clean consumer
first-use under 10 minutes, contributor orientation under 15 minutes, and release
documentation review before publication.

**Constraints**: Documentation must not overclaim maturity, platforms,
performance, package availability, support commitments, security process, or
future bindings. It must be clear English, project-specific, free of unresolved
placeholders, internally linked, consistent with package metadata and existing
contracts, and maintainable when public API, package metadata, compatibility, or
policy decisions change.

**Scale/Scope**: Documentation covers first-time evaluators, package consumers,
production reviewers, future language implementers, contributors, and
maintainers. Scope includes repository overview, getting started, usage,
contract references, lifecycle/diagnostics/error guidance, examples, package
metadata, changelog/release guidance, license/security/support/contribution
policies, issue templates, and pull request guidance.

## Phase 0 Research Summary

See [research.md](research.md).

Key decisions:
- Use root-level GitHub documentation files plus `.github` templates for
  repository discovery and contribution workflows.
- Treat the current runtime package, XML comments, and
  `specs/001-frame-memory-store/contracts/` as the behavior source of truth.
- Document the package as prerelease `0.1.0` unless release metadata changes
  before implementation.
- Use the existing MIT package license metadata as the selected license baseline
  and add the matching `LICENSE` file.
- Use repository-local Markdown/PowerShell validation rather than introducing a
  documentation site generator.
